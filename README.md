# Control Tower Application

Control Tower is an internal monitoring and reporting dashboard built with an ASP.NET Core Web API backend and a lightweight Vanilla JavaScript frontend. It is designed to track factory line production metrics, cycle times, and inspection reports across various lines and stations.

## ⚙️ Technical Details

### Architecture
* **Frontend**: HTML5, CSS3, Vanilla JavaScript (ES6) served statically via `wwwroot`. No heavy frontend framework (React/Angular/Vue) is used, ensuring maximum performance and easy maintainability.
* **Backend**: ASP.NET Core Web API.
* **Data Access**: [Dapper](https://github.com/DapperLib/Dapper) micro-ORM for high-performance SQL Server data retrieval.
* **Database**: Microsoft SQL Server.
* **Real-time SCADA ingestion**: [MQTTnet](https://github.com/dotnet/MQTTnet) v5 client, run as an ASP.NET Core `BackgroundService`, bridging the plant MQTT broker into a pollable REST snapshot (see Fire Hydrant Monitoring below).

### Third-Party Frontend Libraries
* **[Chart.js](https://www.chartjs.org/)**: Renders dynamic, responsive dashboards and charts.
* **[Flatpickr](https://flatpickr.js.org/)**: Provides sleek, lightweight datetime pickers for report filtering.
* **[ExcelJS](https://github.com/exceljs/exceljs)**: Builds the Excel (.xlsx) exports of every report on the client side.

---

### Project Structure
Every feature is a self-contained module: its backend lives in `Modules/<Module>/` and its frontend in `wwwroot/js/<area>/<module>.js` + `wwwroot/css/<area>/<module>.css`. C# namespaces are unchanged (`ControlTower.Controllers` / `.Services` / `.Models`); the folders only group files.

```
Program.cs                         Registers each module (AddReportsModule / AddFireHydrantModule / ...)
appsettings.json                   Single config file for every module (see Configuration below)
Modules/
  Shared/                          ConfigurationController (version, line dropdown), MqttStatusController (header MQTT pill), ApiDateTime (UTC->local fix), KepwareValueParser
  FireHydrant/                     Controller, MQTT service, state store, alert/pump-count/pump-duration loggers + repos, FireHydrantModule.cs
  GasLeak/                         Controller, MQTT service, state store, alert monitor + repo, GasLeakModule.cs
  Ems/                             EmsController, solar MQTT service + state store, SolarData/SolarLiveGraph repo, OtherPowerSource repo, EmsModule.cs
  EbRtm/                           Controller, MQTT service, state store, reading logger, power-failure monitor, energy calculator, EbRtmModule.cs
  Reports/
    ReportsModule.cs               Registers every report service
    LineReports/                   Biometric Shiftwise / Engine No & Barcode, Main Line Cycle Time, Poke Yoke (shared ReportsService)
    QHold/                         Engine QHold Report            -> dbo.usp_GetQHoldReport
    CylinderHeadLeak/              Cylinder Head Leak Rejection    -> dbo.usp_GetCylinderHeadLeakRejectionReport
    CategorywiseRework/            Categorywise Rework (EA01/EA02) -> dbo.usp_GetCategorywiseReworkReport
    SummaryReport/                 Summary Report (Leak/PDI/Testing, EA01/EA02) -> dbo.usp_GetSummaryReport
wwwroot/
  index.html                       Shell: sidebar (Dashboards, then Reports > Biometric / Production / Quality), one tab-pane per screen
  js/core.js                       switchTab, logout, header (version, MQTT pill, line dropdown), shared helpers - loaded first
  js/dashboards/                   fire-hydrant.js, gas-leak.js, ems-renewable.js, eb-rtm.js
  js/reports/                      biometric.js, main-line.js, poke-yoke.js, qhold.js, cylinder-head-leak.js, categorywise-rework.js, summary-report.js
  css/style.v2.css                 Shared shell styles (also used by login.html)
  css/dashboards/, css/reports/    One stylesheet per module
```

All scripts are plain classic `<script>` tags (no bundler) sharing the global scope, loaded in the order listed in `index.html`: `core.js` first, then dashboards, then reports. Static files are served with `Cache-Control: no-cache`, so browsers revalidate and never run a stale script/stylesheet after a deploy (the `?v=` query strings are kept as an extra safeguard).

**Adding a module:** create `Modules/<Name>/` with its controller/services/models and a `<Name>Module.cs` (`AddXxxModule` extension), call it from `Program.cs`, add its settings section to `appsettings.json`, add `wwwroot/js/.../<name>.js` + `css/.../<name>.css` and their tags in `index.html`, a `tab-<name>` pane, a sidebar entry, and its start/stop hook in `switchTab()` (`core.js`).

## 🔄 Functional Flow

### 1. Global Configuration
The application is governed by a **Global Dashboard Line Dropdown** located in the top navigation bar. The values for this dropdown (e.g., `JEA1_New`, `JEA2`) are dynamically populated from `appsettings.json` -> `DashboardDropdownValues`. Changing this dropdown dictates the context for all subsequent data queries.

### 2. Dashboards Tab
* Serves as the landing page.
* Features a high-level overview of production lines.
* Data visualizations are powered by Chart.js.
* **Sidebar**: Collapses to an 80px icon rail by default on desktop (`assets/logo-small.png` shown when collapsed) with a toggle button; state persists via `localStorage.sidebarExpanded`. All nav items, including sub-menu entries, show tooltips on hover.
  * **Menu order**: **Dashboards** (Overview, Fire Hydrant, LPG Gas Leak, EMS Renewable, EB-Real Time Monitoring) first, then **Reports**, which has three sub-groups: **Biometric** (Biometric Shiftwise, Engine NO & Barcode), **Production** (Main Line Cycle Time, Summary Report) and **Quality** (Engine QHold, Cylinder Head Leak Rejection, Categorywise Rework, Poke Yoke Overall / Summary). All menus start collapsed. Each report/dashboard entry has an `id="nav-<tab>"`, so `switchTab()` can highlight it when called programmatically (e.g. a shared `?report=summary` link) and expand the menus it sits in.
  * **Accordion menus**: `toggleSubmenu()` (inline script in `index.html`) closes the other open menu at the same level when one is opened (Dashboards vs Reports; Biometric vs Production vs Quality), so the sidebar stays short. Clicking an open menu still closes it.
  * **Compact + scrollable**: the "Sidebar navigation: compact spacing + scrollable menu" block at the end of `css/style.v2.css` tightens row spacing (sub-items 6px/10px padding, 14px text; nested Reports items 13px; 16px gap under the logo, 12px under the toggle). In the expanded sidebar the `<nav>` list scrolls on its own between the fixed logo/toggle and the ID badge/version, so nothing is cut off on short screens. The collapsed 80px rail does not scroll (a scroll container would clip its hover tooltips, which render outside the rail) and drops the sub-menu indentation so nested icons stay centred. The block must stay last in the file: it overrides earlier `.nav-item` padding rules that use `!important`.
* **Fire Hydrant Monitoring** (`#tab-fire-hydrant`): A SCADA/P&ID-style dashboard for the factory's fire hydrant and sprinkler system. Every datapoint — tanks, diesel level, pump on/off state, pump run counts, the two pressure gauges, and the Shopfloor Pressure grid — is **live**, sourced from the plant MQTT broker (see "Fire Hydrant Live Data" below). The frontend polls `GET /api/firehydrant/status` every 3s while the tab is active (`startFireHydrantPolling()`/`stopFireHydrantPolling()` in `js/dashboards/fire-hydrant.js`, started/stopped on tab switch) and mutates `SCADA_TANKS`/`SCADA_DIESEL`/`SCADA_PUMPS`/`SCADA_GAUGES`/`SCADA_PRESSURE_POINTS` in place via `applyFireHydrantStatus()`. Rendered by `renderScadaDashboard()`, it has three sections:
  * **Water/Diesel Tanks**: CAD-style tank illustrations (header/nozzles, ladder, brick partition, level color-scale, butterfly-valve outlets) showing live-style fill % with green (>75%), yellow (50–75%), red (<50%) bands. The fill percentage text (`.scada-tank-pct2`) is bright white/bold — it used to be a near-black green (`#0b1f14`) that only read clearly against a high fill's light-green background and was nearly invisible on an empty/low tank's plain dark background.
  * **Pump Manifold**: A 5-branch piping manifold (Diesel, Hydrant Main, Hydrant Jockey, Sprinkler Jockey, Sprinkler Main pumps) laid out with CSS Grid; piping is drawn dynamically into an SVG layer (`layoutScadaManifoldPipes()`) using `getBoundingClientRect()` measurements of the actual rendered valve/gate positions, so pipes stay pixel-aligned to components regardless of layout changes. Each pipe (bottom header, Hydrant Line, Sprinkler Line) renders as one continuous 3D-gradient "tube" body, but its red-dashed flow overlay is **segmented per pump branch tap-in point** rather than lighting the whole pipe uniformly — `scadaFlowGroups()` (`js/dashboards/fire-hydrant.js`) computes, per pump-on/off state, exactly which segments actually carry water:
    * **Bottom header**: lit from the tanks rightward up to (and including) the tap-in point of the *rightmost* running pump — computed as a right-to-left running-OR scan over `[diesel, hmain, hjockey, sjockey, smain]`.
    * **Hydrant Line**: lit left-to-right starting at the *leftmost* running hydrant-side pump (diesel/hmain/hjockey) and continuing to the outlet — a left-to-right running-OR scan, the mirror image of the bottom header's.
    * **Sprinkler Line**: same left-to-right scan, but its leftmost segment is fed by the cross-connect (lit whenever *any* hydrant-side pump is running) rather than by a pump directly, before sjockey's and smain's own segments extend it further right.
    * **Cross-connect**: a non-return valve, so it (and therefore Hydrant Line's reach into Sprinkler Line) only carries flow when a hydrant-side pump is on — sprinkler-side pumps (sjockey/smain) can light the Sprinkler Line and bottom header but never the Hydrant Line or cross-connect, matching the check valve's one-way behavior.
    * Branch valve glow (`.scada-valve-img.flowing`) and pump-icon spin (`.scada-branch.running`) stay scoped to that specific pump's own on/off state, unchanged.
    
    Each pump card's "Count" readout is now live (see Live Data below). The Hydrant/Sprinkler Pressure gauges below the manifold (`scadaGaugeSvg()`) draw threshold-driven zone arcs plus tick marks and numeric labels every 2 bar (0/2/4/6/8/10), reusing the `ebDescribeArc()`/`ebPolarToCartesian()` polar-math helpers from the EB-Real Time Monitoring gauges: red 0–4.5, yellow 4.5–6, green 6–8, yellow 8–9.5, red 9.5–10.
  * **Header row**: the heading, Hydrant/Sprinkler Line legend, alert bell, and Demo/Reports buttons all live in one `.scada-header-row` flex row (`justify-content:space-between`, `align-items:center`) — heading on the left, legend+controls (`.scada-header-right`) on the right — so everything shares one vertical-center baseline instead of being independently absolute-positioned at different offsets (a prior version had them 18–26px apart vertically; before that, an even earlier version placed them off-screen entirely at the far edge of the 2000px canvas, unreachable without scrolling all the way right — both fixed by making this a normal flex row sitting *outside* `.scada-canvas`, unaffected by its scroll/scale). The Alerts button is a yellow bell icon (`#fireHydrantAlertBellBtn`, Material Symbols `notifications`) with a small red "!" badge (`#fireHydrantAlertBellBadge`) shown whenever at least one alert is currently listed in the popup (same due/visible filter as the table); clicking it opens the popup. **Reports** opens the Report screen (see below); **Demo** remains a visual-only placeholder, no click behavior wired yet.
  * **Viewport scaling**: `.scada-canvas` (native 2000×590 coordinate space) is enlarged via a JS-computed `transform: scale(...)`, not a fixed CSS value — `fitScadaCanvasScale()` (`js/dashboards/fire-hydrant.js`) measures `.scada-canvas-wrap`'s actual `clientHeight` on every render (and on window `resize`, which Chrome's page-zoom also fires) and sets `scale = clamp(0.85, 1.6, availableHeight / 590)`, so the canvas always fills the available height at whatever browser zoom/OS display-scaling combination is in effect, without ever overflowing it. A fixed scale tuned for one specific zoom level (first built for 1366×768 @ 80%) turned out to overflow at other zoom levels (e.g. 75%, or 1366×768 with no zoom at all) — and because `.scada-canvas` has an opaque background, an overflowing canvas doesn't just look cramped, it visually **paints over the header row above it**, making the heading/legend/buttons appear to vanish entirely. `transform-origin: left center` keeps the canvas's left edge pinned in place regardless of scale (a `center` origin was tried first and silently pushed the left edge into negative, unreachable territory, hiding the water tanks and part of the gauges off-screen). `.scada-canvas-wrap` (`flex:1;display:flex;align-items:center;`) fills all vertical space below the header row and vertically centers the canvas within it — no `justify-content:center` on the horizontal axis, since centering a flex item wider than its container makes its start unreachable by scrolling, and the canvas is deliberately wider than the viewport (Shopfloor Pressure grid). Because `getBoundingClientRect()` reflects the *scaled* on-screen size while the SVG's own path coordinates are still in native 2000×590 units, `layoutScadaManifoldPipes()` divides every measured on-screen delta by `canvasRect.width / canvas.offsetWidth` (the live scale factor, read fresh each call rather than assumed) before using it as a path coordinate — otherwise every pipe/valve position would be scaled twice and the flow overlay would drift off the visible pipes.
  * **Diesel tank readout position**: the small diesel-level box (`.scada-diesel-box`, the "0%"-style readout — distinct from the two large water tanks) is rendered as an independent element appended after the 5 pump branches in `renderScadaManifold()`, with a `.scada-diesel-label` ("Diesel Tank") directly above it, both absolutely positioned within `.scada-manifold-grid` at `left:20%` (the boundary between grid columns 1 and 2, i.e. between the Diesel Pump and Hydrant Main Pump columns) with `transform:translateX(-50%)` to center them on that boundary — `top:35px` for the label, `top:55px` for the box below it, clearing the top header pipe rather than overlapping it (its previous position, stacked directly above the Diesel Pump column, visually cut through that pipe). `renderScadaDiesel()` still fills the box via the generic `.scada-diesel-box[data-diesel]` selector, unaffected by where in the DOM it lives.
  * **Alerts popup**: Clicking **Alerts** (`openFireHydrantAlerts()`) shows `#fireHydrantAlertsOverlay` — a checkbox/Timestamp/Type/Description table backed by `GET /api/firehydrant/alerts`, sourced from the DB-backed alert log (see "Fire Hydrant Alerts" below, and API Details). The popup **only ever opens when clicked** — there is no auto-reopen timer. A snoozed-and-not-yet-due alert is hidden from the table entirely (`renderFireHydrantAlertsTable()` filters via `fireHydrantAlertIsDue()`), not merely greyed out, and reappears automatically once its snooze passes (assuming the condition is still abnormal). The **Snooze** button (`#fireHydrantSnoozeBtn`) starts disabled and only enables once at least one row is checked (event-delegated on the tbody, since rows are recreated every render); there is no Dismiss button — the header's "×" is the only way to close the popup, independent of alert state. Checking one or more rows, picking a date/time in the Flatpickr **Snooze till** picker, and clicking **Snooze** calls `snoozeFireHydrantAlerts()`, which `POST`s to `/api/firehydrant/alerts/snooze`. While the Fire Hydrant tab is active, `fetchFireHydrantAlerts()` polls every 20s (folded into `startFireHydrantPolling()`/`stopFireHydrantPolling()`) purely to keep the table/caution-icon data fresh in the background.
  * **Snooze suppresses the caution icon too**: `scadaAnyRedCondition()` cross-references each red condition's would-be alert Description against `fireHydrantSnoozedDescriptions()` (built from the same `GET /api/firehydrant/alerts` response, via JS-side description generators mirroring the backend's exact templates) and excludes anything currently snoozed — so snoozing an alert also hides the caution icon for that specific condition, while any other unsnoozed red condition still shows it.
  * **Caution icon**: `assets/Caution.gif` appears at the bottom edge of the "Feedback to Controller" panel (`#scadaCautionIcon`, toggled by `updateScadaCaution()` at the end of every `renderScadaDashboard()` call) whenever `scadaAnyRedCondition()` finds any of: a tank/diesel level in the red band (`scadaLevelClass() === 'fault'`), or a pressure gauge / Shopfloor Pressure point in the red band (`scadaPressureColor() === '#FF0000'`). Hidden otherwise.
  * **Report screen**: clicking **Reports** (`openFireHydrantReport()`) shows `#fireHydrantReportOverlay` — a full-size modal (`95vw × 90vh`, distinct from the smaller Alerts popup), with a From/To Flatpickr date-time range, a **Download CSV** button, and three tabs (**Duration**, **Count**, **Alerts**) switched via `switchFireHydrantReportTab()`, all backed by real data. The **Duration** tab (S.No / Pump / Start Time / End Time / Duration, the default tab) calls `GET /api/firehydrant/pumpduration/sessions?start=...&end=...` — one row per individual pump run session, `Duration` trimmed client-side from .NET's raw `hh:mm:ss.fffffff` to `hh:mm:ss` via `formatDuration()` — see "Fire Hydrant Pump Duration" below. The **Alerts** tab's grid (S.No / Type / Description / Start Event / End Event) calls `GET /api/firehydrant/alerts/history?start=...&end=...`, pairing each alert's open row (Start Event) with its close row (End Event, shown as "Ongoing" if `null`/still open) — see "Fire Hydrant Alerts" below. The **Count** tab (S.No / Pump / Start Count / End Count / Run Count) calls `GET /api/firehydrant/pumpcount/summary?start=...&end=...` — see "Fire Hydrant Pump Count" below. **Download CSV** (`downloadFireHydrantReportCsv()`) exports whichever tab is currently active as a client-generated CSV blob (no server round-trip). The From/To inputs (`.scada-alerts-snooze-input`, shared with the Alerts popup's Snooze-till picker) use `background: var(--white)` — it was originally a hardcoded `#1e1e1e`, which combined with the already theme-aware `color: var(--dark)` produced unreadable dark-text-on-dark-background in light mode.
  * **Timezone gotcha (fixed)**: the frontend sends date-range/snooze values via JS's `toISOString()`, which is always UTC (`Z`-suffixed). ASP.NET Core's model binder parses that into a `DateTime` with `Kind=Utc` but does **not** shift the value to local time, while every datetime stored in these tables is local server time (`DateTime.Now`). Left uncorrected, a report query or snooze deadline silently landed 5.5h (IST) off from what the user actually picked — a query for "the last 24 hours" would miss the most recent ~5.5h of data, and a snooze could expire immediately instead of persisting. `ApiDateTime.ToLocal()` (shared by all dashboard controllers, `Modules/Shared/ApiDateTime.cs`) converts every incoming UTC-kind `DateTime` (report `start`/`end`, snooze's `SnoozeUntil`) to local time before use; a plain (non-`Z`) value is left as-is.
  * **Shopfloor Pressure**: A coordinate-based schematic positioned beside (not below) the pump manifold, built from a fixed-size `position:relative` container (`.pipe-schematic`) with a single absolute `<svg class="pipe-svg">` layer (`overflow:visible`, z-index 0) drawing every pipe segment as `#800000` maroon `<path>`s at hardcoded coordinates, and `.pipe-card` widgets (z-index 1, transparent background, thin `#555` border) positioned on top via explicit `left`/`right`/`top` pixel values — left-column cards (Machine Shop, Engine Assembly, Vehicle Assembly) use `right`, right-column cards (Canteen, Paint Shop 2, Paint Shop 1) use `left`. EV Building sits above G120 with its own vertical connector; G120/RO ETP & STP/Fire Hydrant/MRS sit on the top branch. FG Warehouse shares Vehicle Assembly's row as a narrower card (`.pipe-card.narrow`) at the leftmost position, connected by its own pipe stub off the spine. Each row's pipe is drawn in two segments (spine → left card edge, then that card's far edge → right card edge) rather than one continuous line, so the pipe visibly stops at each card border instead of passing behind it. Values use a digital/7-segment-style monospace readout colored by `scadaPressureColor()` in `js/dashboards/fire-hydrant.js` — the same red/yellow/green pressure bands as the gauges above (red `<4.5` or `>9.5`, green `6–8`, yellow otherwise) rather than a plain zero/non-zero split. `ro` and `mrs` have no MQTT source and always render blank. The whole canvas background and card label color follow the app's light/dark theme via CSS custom properties (`var(--background)`, `var(--dark)`), so the schematic stays legible in both modes.
* **EMS Renewable** (`#tab-ems-renewable`): A bento-box industrial dashboard for the Vallam renewable energy source, laid out with CSS Grid (`.ems-grid`, 62%/38% columns) rather than the SCADA canvas's absolute positioning. Most data is still a mock JS constant (`EMS_VOC`); **`EMS_SOLAR`'s Live/Today/Yesterday/MTD+hourly chart, `EMS_SOURCES`' previous/current-month values+%, `EMS_GREEN`'s CO2 Reduction/month labels (see "EMS Other Power Source" below), and `EMS_CONTRIB`'s bars 3-4 (bars 1-2 stay session-local, see below) are live** (see "EMS Solar Live Data" below), polled every 5s (status) / 60s (hourly chart) by `fetchEmsSolarStatus()`/`fetchEmsSolarGraph()` (`startEmsSolarPolling()`/`stopEmsSolarPolling()`, tied to tab switch same as Fire Hydrant/GasLeak). Rendered by `renderEmsRenewable()`, with four Chart.js charts built in `emsRenderCharts()`: a Green Energy source-mix donut, a VOC pink bar chart, a Roof Top Solar spline-area chart (neon-green gradient fill), and a Green Power Contributions bar chart (`EMS_CONTRIB`) using a small inline `emsValueLabelPlugin` (a `chartjs-plugin-datalabels` substitute, since that plugin isn't bundled) to print values above each bar. `EMS_CONTRIB` is now live/dynamic rather than fully mock: bars 1-2 (`values[0]`/`[1]`) are session-local figures entered as Graph Val 1/Graph Val 2 in the "Green Power Contribution Input" tab (`emsSaveOtherPower()`, still no backend), bars 3-4 are the **sum of the 5-source PERC column** (`EMS_SOURCES.reduce((sum, s) => sum + s.prevPct/currPct, 0)`, same computation as the `emsSourceFooterPct` footer, just for both months) set in `fetchEmsOtherSourceSummary()`; labels (`EMS_CONTRIB.labels`) are recomputed every `renderEmsRenewable()` call via two small date helpers, `emsFiscalYearLabel(date)` (Indian FY, Apr-Mar, e.g. "FY 26-27") for bars 1-2 and `emsShortMonthLabel(date)` (e.g. "Oct - 2026") for bars 3-4, always reflecting the previous/current FY and calendar month relative to today. The donut (`EMS_SOURCES.map(s => s.currPct)`, colors keyed by source name in `emsDonutColors`) additionally uses `emsDonutLabelPlugin()` — a small inline plugin, same idea as the bar-label one — to draw each source's name directly on its slice at the slice's mid-angle/mid-radius (white text, drop shadow for contrast against any fill color) instead of requiring a tooltip hover to identify it; a slice is skipped (no label drawn, chord length `sweep × midRadius < 24`) when it's too thin for legible text — `0%`/`1%` slices fall back to the default Chart.js hover tooltip. The VOC "Actual Status" gauge is a hand-built SVG semicircle (`emsGaugeSvg()`), following the same arc/needle pattern as the Fire Hydrant gauges. Same `0`/`>0` → muted-blue/neon-green value coloring convention as the SCADA dashboards. Like the Fire Hydrant screen, colors are driven by the app's theme CSS variables (`var(--background)`, `var(--white)`, `var(--dark)`, `var(--gray)`, `var(--neutral)`) so it adapts to light/dark mode; `emsRenderCharts()` additionally picks Chart.js text/grid colors based on `document.body.classList.contains('light-mode')` (same pattern as the existing Pareto chart), and `applyTheme()` re-renders the EMS charts on the fly if that tab is active when the theme toggle changes. The Green Energy card's **Total Green Power / Total Units** box (`.ems-total-bar`) sits to the right of the % of Green Energy/CO2 Reduction stat blocks, pushed there via `margin-left:auto` inside the shared flex `.ems-stats-row` so it lines up directly under the previous-month|current-month toggle. The source table's **`% of Green Energy` footer** (`emsSourceFooterPct`) is the live sum of `EMS_SOURCES`' current-month `currPct` values (reads ~100% when the 5 sources' percentages are internally consistent), not a hardcoded figure.
  * **"Other Source" popup**: an `.ems-othersource-btn` button next to the date badge (`openEmsOtherSourceModal()`) opens a full-size 3-tab modal (`#emsOtherSourceModal`, `switchEmsOtherSourceTab()`) for manually entering figures the plant has no MQTT tag for. The tab **labels are intentionally swapped from their underlying pane/data wiring** (a deliberate late UI tweak — only the visible text moved, not the `data-emstab`/`onclick` behavior), so by position: 1st tab, labeled **"Other Power Source"**, opens `emsOsPaneGreen` (`data-emstab="green"`) — Third Party Wind/Solar, TNEB, DG, Solar, GCP Solar, IEX Renewable/Non-Renewable + a month picker, **backed by the DB** (see "EMS Other Power Source" below). 2nd tab, **"VOC Inputs"**, opens `emsOsPaneVoc` — Total/Live Station, Actual Status, and 12 dynamically-built Stag fields (`emsBuildVocStagFields()`); `emsSaveVoc()` only `console.log`s for now, no backend yet. 3rd tab, labeled **"Green Power Contribution Input"**, opens `emsOsPaneOther` (`data-emstab="other"`) — a month picker plus Graph Val 1/2/3 and Max Demand fields (`.ems-os-field-grid-1`, single narrow column, matching the reference ThingWorx mashup's own "Green Power Contribution Input" tab), `emsSaveOtherPower()` still `console.log`-only; its real backend/table shape is still pending a spec from the plant team.
* **EB-Real Time Monitoring** (`#tab-eb-rtm`, `js/dashboards/eb-rtm.js`, `Modules/EbRtm/`): 33KV EB Incomer (meter `VLM_EMS.Meter4_SID7`) monitoring, split 18%/82% into a sidebar and a main workspace. **Live** from MQTT topic `EbRtm:Mqtt:Topic` (`vlmEnergyMonitoring`): `EbRtmMqttBackgroundService` → `EbRtmStateStore` (voltage/power/demand tags arrive in V/W/VA and are divided by 1000; the Real Energy register is kept raw and only divided by 1000 for display).
  * **Sidebar**: Max Demand (vs `EbRtm:MaxDemandLimitKva`), Present Demand, Power Failure duration/count for today (a failure = average voltage < 0, tracked by `EbRtmPowerFailureMonitor` in `EbCPowerFailureEvents`), and Energy Consumption (kWh) per shift All/A/B/C for current vs previous day (`EbRtmEnergyCalculator`: difference of the Real Energy register between shift boundaries from `ShiftConfiguration`; "All" = 00:15 to next 00:15).
  * **Logging**: `EbRtmReadingLogger` writes one full meter snapshot to `[ControlTowerVLM].[dbo].[EbCMonitoring]` per clock-aligned `EbRtm:LogIntervalMinutes` slot (default 5 → 10:00, 10:05, ...); restart-safe (seeds the last slot from the newest row).
  * **Date picker** (topbar, flatpickr, `dd/mm/yyyy`, no future dates): drives the charts only - gauges and sidebar always stay live. While today is selected the active chart refreshes every 60s.
  * **Filter tabs** (`EB_FILTERS`, `ebSelectFilter()`): **ALL** = the 5-gauge row + 2×2 trend grid (Voltage/Frequency/PF/Current) for the selected day; **Voltage / Frequency / Power Factor / Current / Max Demand** = one large area chart of the selected day on a fixed 00:00-24:00 axis (`GET /api/ebrtm/history`), Current with a dashed 150 A line and Max Demand with a dashed Max Limit line; **Power Failure Duration / Count** = bars for the 7 days ending on the selected date (`GET /api/ebrtm/powerfailure/daily`); **Energy Consumption** = one point per completed day of the selected date's month, days without data left out (`GET /api/ebrtm/energy/daily`). Empty days show "No data logged ..."; a failed request shows the HTTP error on the chart.
  * **Gauges** (`EB_GAUGES`, `ebGaugeSvg()`): 270° speedometer dials with 5 labelled divisions × 5 minor ticks, thick red/orange/green zone arc, tapered needle and value box both coloured by the zone the value is in (black text). Red at both ends for Voltage (<25 / >37.5 kV), Frequency (<46.5 / >53 Hz), Current (<20 / >175 A) and Active Power (<900 / >8250 kW); the Current and Active Power low limits are provisional placeholders to be confirmed by the plant. Power Factor is red below 0.95.
  * Endpoints: `GET /api/ebrtm/status` (live, in-memory), `/history`, `/energy`, `/energy/daily`, `/powerfailure/daily`.

### EMS Solar Live Data (MQTT → REST bridge)
`EmsSolarMqttBackgroundService` subscribes to `Ems:Mqtt:SolarTopic` (`vlmsolarlivetag`, shared `Mqtt` broker), tracking 2 feeder meters' `Active power`/`FWD Real Energy` (`EmsSolarStateStore`). `GET /api/ems/solar/status` returns `live` (kW, sum of both meters' power ÷1000), `today`/`yesterday`/`mtd` (kWh, deltas of summed cumulative Real Energy against daily 00:15 baseline rows in `[ControlTowerVLM].[dbo].[SolarData]` via `SharedDataConnection` (database from `Ems:Database`), `EmsSolarDataRepository`). The background service inserts that baseline row itself once per day (first message seen in the 00:15 minute). If today's row isn't there yet (before 00:15), both Today/Yesterday shift back a day. `mtd` = current day's 00:15 baseline (the same `baseline0` Today/Yesterday use, inheriting that same before-00:15 fallback) minus the previous month's last recorded 00:15 baseline (`GetLatestRealEnergyBeforeAsync(firstOfThisMonth)` — the latest row strictly before the 1st of the current month, rather than assuming a row exists for the exact calendar-last-day, since a day's insert can be missed). Same service also logs one hourly point (rounded Live kW, first message seen in each HH:15 minute) to `[ControlTowerVLM].[dbo].[SolarLiveGraph]` (TimeStamp/Solar, no id column) for the chart; `GET /api/ems/solar/graph` returns only today's points (`CAST(TimeStamp AS DATE) = today`), so the chart naturally resets at midnight. Frontend polls it every 60s (`fetchEmsSolarGraph()`) and updates the existing Chart.js instance in place (`chart.update()`) rather than destroying/recreating it.

### EMS Other Power Source (manual monthly input, no MQTT)
The "Other Source" popup's Green Power Contribution Input tab (`emsOsPaneGreen`, currently labeled "Other Power Source" in the tab bar - see the swapped-label note in the modal markup) submits one row per month to `[ControlTowerVLM].[dbo].[OtherPowerSource]` (`ThirdPartyWind`/`ThirdPartySolar`/`TNEB`/`DG`/`Solar`/`GCPSolar`/`IEXRenewable`/`IEXNonRenewable`, all bigint kWh) via `POST /api/ems/othersource` (`EmsOtherPowerSourceRepository.InsertAsync`, `emsSaveGreenPower()`). `GET /api/ems/othersource/summary` returns the previous and current calendar month's latest row (`GetLatestForMonthAsync`, ordered by `TimeStamp DESC, id DESC` so a re-submitted month uses the newest entry), converts the 5 sources shown in `ems-source-table` (GCPSolar/ThirdPartySolar/ThirdPartyWind/IEXRenewable/Solar - the last mapped to the "Roof Top Solar" row) from raw kWh to lakhs (÷100000), and computes each source's % share of that month's 5-source total. The same endpoint also returns `co2` per month: `Math.Round(0.716 * rawSum / 1000)`, where `rawSum` is deliberately the **un-divided** raw-kWh sum of those same 5 columns (the same scale `GetOtherPowerSourceHistory` returns) rather than the ÷100000 "lakhs" figures used for the table/percentages — using the lakhs-scale sum here rounded to 0 for realistic data, which is why `BuildOtherSourceMonthSummary` computes `rawSum` as a separate, parallel value just for this field. The endpoint also returns `totalGreen` (= the same lakhs-scale `sum` as the 5-source total, i.e. GCPSolar+ThirdPartySolar+ThirdPartyWind+IEXRenewable+Solar) and `totalUnits` (`sum` plus TNEB/DG/IEXNonRenewable, also lakhs-scale) per month, rendered into the Total Green Power/Total Units box as `prev | curr`, plus `pctGreen = (sum / totalUnits) * 100` (the single "% of Green Energy" headline stat — only the **current** month's value is used, there's no prev/curr split for this one field). `fetchEmsOtherSourceSummary()` maps the response onto `EMS_SOURCES`' `prev`/`prevPct`/`curr`/`currPct` fields, `EMS_GREEN.monthPrev`/`monthCurr`, `EMS_GREEN.co2Prev`/`co2Curr` (rendered into `emsCo2` as `co2Prev | co2Curr`), `EMS_GREEN.totalGreenPrev`/`totalGreenCurr`/`totalUnitsPrev`/`totalUnitsCurr`, and `EMS_GREEN.pctGreen` (from `data.current.pctGreen`), then re-renders via `renderEmsRenewable()`. Called once per EMS tab switch (not polled) and again right after a successful save. `GET /api/ems/othersource/history` returns the full table (raw kWh, newest first) for that same pane's data grid (`emsOsGreenTbody`/`emsOsGreenEmpty`, `fetchEmsOtherSourceHistory()`), fetched when the popup opens and again after a save.

### Fire Hydrant Live Data (MQTT → REST bridge)
Unlike the Reports tab's SQL Server/Dapper pattern, Fire Hydrant Monitoring's live values come from the plant MQTT broker, not a database:
* **`FireHydrantMqttBackgroundService`** (`Modules/FireHydrant/`): an ASP.NET Core `BackgroundService` that opens a single connection to the broker (`Mqtt:Host`/`Mqtt:Port` from `appsettings.json`) and subscribes to **two** topics on it — `Mqtt:Topic` (`vlmfirehydrantpumproom`: tanks/diesel/pumps/gauges) and `Mqtt:OtherLocationsTopic` (`vlmfirehydrantotherlocation`: the Shopfloor Pressure grid) — routing each incoming message to the matching `FireHydrantStateStore` update method by topic name. Reconnects every 5s on failure/disconnect rather than crashing the host.
* **Payload shape** (same on both topics): `{ "timestamp": <epoch ms>, "values": [{ "id": "<tag>", "v": <number>, "q": <bool quality>, "t": <epoch ms> }, ...] }`. Values with `q:false` are ignored (the last good value is kept) rather than trusted.
* **`FireHydrantStateStore`** (`Modules/FireHydrant/`): a thread-safe singleton holding the latest mapped snapshot, updated by two methods:
  * `UpdateFromPayload()` (pump room topic) maps `FireHydrant.Hydrant.Fire Tank1`/`Fire Tank2` → the two water tank levels, `DieselTank` → diesel level, `HydrantTank`/`SprinklerTank` → the two pressure gauges (raw value ÷ 100 = bar, since the transmitters report 0–1000 for a 0–10 bar range), the five `... On\Off status` tags → each pump's `running` flag, and `DieselTankcount`/`Hydrant Count`/`Jockey Pump 1`/`Jockey Pump 2`/`Sprinkler Count` → each pump's `Count` badge (Diesel/Hydrant Main/Hydrant Jockey/Sprinkler Jockey/Sprinkler Main respectively). It also mirrors the Hydrant Pressure gauge value into the Shopfloor Pressure grid's `fh` point, since Fire Hydrant reuses that same reading rather than having its own MQTT tag.
  * `UpdateFromOtherLocationsPayload()` (other-locations topic) maps `Firehydrant_otherLocations.EV.EV` → `ev`, `G120.G120` → `g120`, `VA_PT.MS` → `machine`, `Canteen.Canteen` → `canteen`, `VA_PT.EA` → `engine`, `PS.PS2` → `paint2`, `VA_PT.VA` → `vehicle`, `PS.PS1` → `paint1`, and `DCD.WaterPressure` → `warehouse`. `ro` and `mrs` have no tag on this topic and stay `null` (default value, kept for the grid's remaining two card slots).
* **`FireHydrantController`** (`Modules/FireHydrant/`): `GET /api/firehydrant/status` returns `FireHydrantStateStore`'s current snapshot (`Models/FireHydrantStatus.cs`, including `pressurePoints`) as JSON (camelCase, ASP.NET Core's default `System.Text.Json` web options) for the frontend to poll.

### Fire Hydrant Alerts (DB-backed)
A red-condition alert log, separate from the live MQTT snapshot above, persisted to SQL Server rather than kept only in memory:
* **Table**: `[FireHydrant].[dbo].[Alerts]` on the same server as `SharedDataConnection` (10.130.1.73) — reached via 3-part cross-database names, same pattern as `ReportsService`. The `factreread` login required an explicit grant to this database (it has no access by default). Columns: `id` (`bigint NOT NULL`, **no identity/default** — assigned as `MAX(id)+1` inside the same `INSERT...SELECT`), `AlertId` (`bigint`, a `yyyyMMddHHmmssfff`-based unique id shared by an alert's "open" and "close" rows), `EventTime` (`datetime2`, added specifically for this feature — the table's pre-existing `DateTime` column is actually a SQL `timestamp`/rowversion type and cannot hold a real date), `Type`, `Description`, `status` (`open`/`close`), `SnoozeTime` (`datetime2 NULL`).
* **Detection — `FireHydrantAlertMonitor`** (`Modules/FireHydrant/`): called after every MQTT payload update (from `FireHydrantMqttBackgroundService`) with the latest `FireHydrantStatus`. Tracks a red/yellow/green "zone" per monitored point and inserts a row only on a *transition*, not every poll:
  * **Water/diesel level** (`Type: "Water level"` / `"Diesel level"`): red when level ≤20% (a separate, stricter threshold than the tank UI's 50%/75% color bands).
  * **Pressure** (`Type: "Water pressure"`): red when <4.5 or >9.5 bar — the Hydrant/Sprinkler gauges plus every Shopfloor Pressure point except `ro`/`mrs` (no MQTT source) and `fh` (mirrors the Hydrant gauge, already covered).
  * **Debounced (10s)**: a reading must sit continuously in a red zone for at least 10 seconds before it's confirmed and acted on (`DebouncedZone()`, per-key candidate-zone + timestamp). This absorbs a single transient bad-but-quality-flagged MQTT reading — observed in practice as 5 unrelated metrics (both tanks, diesel, hydrant/sprinkler pressure) all flipping red and back within under a second — without meaningfully delaying a genuinely sustained condition.
  * Entering red inserts a `status: "open"` row with a freshly generated `AlertId`; leaving red inserts a `status: "close"` row with that *same* `AlertId`. The open row is never mutated — closing is always a new row, so the table is an append-only audit trail.
  * **Restart-safe (no duplicate opens)**: in-memory zone tracking alone would forget an already-open alert across an app restart and re-insert a duplicate "open" row for a condition that's still red. `InitializeFromDbAsync()` (called lazily on the first `EvaluateAsync`) seeds `_zones`/`_openAlertIds`/`_snoozeUntil` from whatever `GetOpenAlertsAsync()` already returns, matching each open row back to its monitored key by its exact `Type`+`Description` (against the fixed `LevelAlertDefinitions`/`PressureAlertDefinitions` tables) — so a still-red condition (snoozed or not) is recognized as already-open across a restart, and only its eventual recovery inserts the matching close row, never a second open row. This was confirmed to have actually happened prior to this fix (duplicate open rows found in the live table from separate restarts) and was verified live afterward with no further duplicates.
  * **Snooze suppresses re-opening, not closing**: `ApplySnoozeAsync(alertIds, until)` (called by the controller immediately after a snooze request persists, and re-seeded from the DB on restart) records a per-key deadline in `_snoozeUntil`. If the condition briefly recovers and re-triggers while that deadline hasn't passed, no new "open" row is created — but a genuine recovery still inserts the "close" row unconditionally (closing happens on the zone-to-normal transition, before the snooze check is ever reached), so a real recovery during the snooze window is still recorded accurately. Once the deadline passes, the next abnormal reading opens a fresh alert normally.
* **`FireHydrantAlertRepository`** (`Modules/FireHydrant/`, Dapper): `GetOpenAlertsAsync()` returns alerts whose *most recent* row (by `AlertId`, latest `EventTime`) is still `status: "open"` — this is what makes a recovered alert disappear from the popup automatically, without touching the historical open row. `InsertAsync()` and `SnoozeAsync()` back the monitor and the snooze endpoint respectively. `GetAlertHistoryAsync(start, end)` backs the Report screen's Alerts tab — pairs each `status: "open"` row with its `status: "close"` row via a self-`LEFT JOIN` on `AlertId` (`EndEvent` is `null` if not yet closed), filtered by the open row's `EventTime` falling in `[start, end]`. Deliberately doesn't return `AlertId` — it's read-only report display, so the JS-precision handling `FireHydrantAlertDto.AlertId` needs isn't worth it here.
* Endpoints: see API Details below.

### Fire Hydrant Pump Count (DB-backed)
Backs the Report screen's Count tab: how many times each of the 5 pumps actually ran in a chosen date range, computed from the MQTT pump-room topic's cumulative run-count tags (`DieselTankcount`, `Hydrant Count`, `Jockey Pump 1`/`2`, `Sprinkler Count`).
* **Table**: `[FireHydrant].[dbo].[PumpRunningCount]` (same server/connection as Alerts). Columns: `id` (`bigint NOT NULL`, no identity — assigned as `MAX(id)+1` on insert, same as Alerts), `DateTime` (a genuine `datetime` this time, unlike Alerts' rowversion trap — checked before writing any code), `Pump` (`nvarchar`, the pump's display label e.g. `"Diesel Pump"`), `Count` (`bigint`).
* **Logging — `FireHydrantPumpCountLogger`** (`Modules/FireHydrant/`): called after every pump-room MQTT payload (not the shopfloor-pressure topic, which doesn't carry pump counts). The tag values are cumulative and the topic publishes every few seconds, so logging every message would flood the table with repeated values — a row is only inserted when a pump's count differs from the last logged value (or on first observation, to establish a baseline), mirroring `FireHydrantAlertMonitor`'s change-detection design. Also restart-safe the same way: seeds its last-known count per pump from each pump's most recent DB row on the first evaluation after startup, so a restart doesn't log a spurious duplicate. **A count of exactly 0 is never inserted** (a 0 isn't a meaningful "it ran" event) — the in-memory last-known-count tracking still updates on every observation regardless, only the DB write is skipped. This is safe because a day with no rows logged yet is already treated as a 0 baseline by `GetSummaryAsync()` below, so omitting explicit zero rows loses no information the calculation needs.
* **Daily reset**: the MQTT tag's cumulative count resets to 0 every day. `FireHydrantPumpCountRepository.GetSummaryAsync(start, end)` accounts for this by summing each calendar day's delta separately rather than a naive `EndCount − StartCount` (which goes wrong — even negative — the moment a report range crosses a midnight reset): a day fully inside the range contributes its last-logged count that day against a 0 baseline (since it just reset), and only the range's first day subtracts whatever had already accumulated before `start`. `StartCount`/`EndCount` in the response are still the raw counter reading at the exact start/end instant (useful for display), but `RunCount` — not their difference — is the real total, and is what the report shows. Verified with a synthetic cross-midnight scenario (50 the day before a reset + 15 the next day → correctly summed to 65, not `15 − 50 = −35`). **Pumps with `RunCount == 0` for the requested range are omitted from the response entirely** — the Count report only lists pumps that actually ran during that window.
* Endpoint: see API Details below.

### Fire Hydrant Pump Duration (DB-backed)
Backs the Report screen's Duration tab: a raw list of every individual pump run session (on → off) in a chosen date range, derived from the same live `Running` state already tracked in `FireHydrantStatus.Pumps`.
* **Table**: `[FireHydrant].[dbo].[Duration]` (same server/connection as Alerts/PumpRunningCount). Columns: `id` (`bigint`, no identity — `MAX(id)+1` on insert, same pattern as the other two tables), `Date`, `Pump` (display label), `StartTime`, `EndTime`, `Duration` (SQL `time`, so capped under 24h — checked all column types/nullability before writing any code). Unlike Alerts (two append-only rows per incident) or PumpRunningCount (one row per change), this table is **one row per complete run session**: `EndTime`/`Duration` are nullable and start `NULL`.
* **Logging — `FireHydrantPumpDurationLogger`** (`Modules/FireHydrant/`): called after every pump-room MQTT payload. Tracks each pump's last-known `Running` boolean; on **off→on** it inserts a new row (`StartTime = now`, `EndTime`/`Duration` left `NULL`) and remembers the new row's `id`; on **on→off** it updates that same row's `EndTime` and computed `Duration` in place.
* **Restart-safe**: on the first evaluation after startup, checks each pump for an existing row with `EndTime IS NULL` (a session already in progress before the restart). If the pump is *still* running, resumes tracking that same row (no duplicate session started). If the pump has *stopped* while the app was down, closes that stale row out immediately using "now" as a best-effort `EndTime` (the true stop time was never observed, so this is the closest available answer rather than leaving it open forever).
* **`FireHydrantPumpDurationRepository`** (`Modules/FireHydrant/`, Dapper): `GetOpenSessionAsync(pump)` (the restart-recovery lookup above), `InsertStartAsync(pump, startTime)` (returns the new row's `id` via `OUTPUT INSERTED.id`), `UpdateEndAsync(id, endTime, duration)`, and `GetSessionsAsync(start, end)` — backs the endpoint below, filtered by `StartTime` falling in `[start, end]`.
* Endpoint: see API Details below.

## 🔌 API Details

The backend exposes RESTful API endpoints; each module has its own controller(s):

### `ConfigurationController.cs` (`/api/configuration`)
* `GET /api/configuration/version` - the `App:Version` string shown in the sidebar.
* `GET /api/configuration/dashboard-dropdown` - the `DashboardDropdownValues` array (header Line dropdown).

### `FireHydrantController.cs` (`/api/firehydrant`)
* `GET /api/firehydrant/status`
  * Returns the current Fire Hydrant SCADA snapshot (tanks, diesel, pumps with counts, gauges, shopfloor `pressurePoints`, `connected`, `lastUpdated`) as maintained by `FireHydrantStateStore` from the live MQTT feed. Never queries the broker directly — always returns the latest cached snapshot, so it's safe to poll frequently.
* `GET /api/firehydrant/alerts`
  * Returns every alert whose latest DB row is still `status: "open"` (see "Fire Hydrant Alerts" above), each with `alertId`, `eventTime`, `type`, `description`, `status`, `snoozeTime`. Includes snoozed alerts (the frontend decides whether to auto-popup based on `snoozeTime`); doesn't touch the live MQTT feed.
* `POST /api/firehydrant/alerts/snooze`
  * Body: `{ "alertIds": [<string>, ...], "snoozeUntil": "<ISO datetime>" }` — **`alertIds` are strings, not numbers.** `AlertId` is a 17-digit `yyyyMMddHHmmssfff` value that exceeds JavaScript's safe integer range, so both `GET /alerts`'s output and this endpoint's input carry it as a string to avoid the browser silently rounding it to a different value; the controller parses each to `long` explicitly (`long.TryParse`, `400` on failure) before use. Sets `SnoozeTime` on the currently-open row for each given `AlertId` (DB), then calls `FireHydrantAlertMonitor.ApplySnoozeAsync()` so the in-memory re-opening suppression takes effect immediately rather than waiting for a restart. Returns `400` if `alertIds` is empty, `204` on success.
* `GET /api/firehydrant/alerts/history?start=<ISO datetime>&end=<ISO datetime>`
  * Backs the Report screen's Alerts tab. Returns one row per alert incident in the range (`type`, `description`, `startEvent`, `endEvent` — `endEvent` is `null` if the alert hasn't closed yet), pairing each open row with its close row by `AlertId` (see `GetAlertHistoryAsync` above). No `alertId` in the response — read-only display, not needed.
* `GET /api/firehydrant/pumpcount/summary?start=<ISO datetime>&end=<ISO datetime>`
  * Backs the Report screen's Count tab. Returns one row per pump that actually ran in the range (`RunCount == 0` pumps are omitted) — `pump`, `startCount`, `endCount`, `runCount` — computed by `GetSummaryAsync()` with the daily-reset-aware day-by-day summation described in "Fire Hydrant Pump Count" above.
* `GET /api/firehydrant/pumpduration/sessions?start=<ISO datetime>&end=<ISO datetime>`
  * Backs the Report screen's Duration tab. Returns one row per pump run session with `StartTime` in the range — `pump`, `startTime`, `endTime` (`null` if still running), `duration` (`null` if still running, otherwise a `TimeSpan` serialized as `"hh:mm:ss.fffffff"`).
  * All three report endpoints (and `alerts/snooze`'s `snoozeUntil`) run their `DateTime` inputs through the shared `ApiDateTime.ToLocal()` first — see the "Timezone gotcha" note above.

### `ReportsController.cs` (`/api/reports`)
* `GET /api/reports/biometric-shiftwise`
  * Fetches Biometric Shiftwise data given `line`, `historyCard`, `startDate`, and `endDate`.
  * Executes the `UNION ALL` logic against historical, pre-shift, and current shift tables.
* `GET /api/reports/biometric-engine-barcode?line=...&historyCard=...&engineNo=...` (or `&barcode=...` instead of `engineNo`)
  * Resolves stations for the Line/HistoryCard, scans the resolved station tables for a matching `Engine_Number`/`Barcode_1/2/3`, then returns the biometric punch(es) recorded during that event's shift window at that station.
  * Requires `line`, `historyCard`, and exactly one of `engineNo` or `barcode`; returns `400` if neither is supplied.
  * Returns `[]` (not an error) when the station/value combination exists but no biometric punch falls within the resolved shift window — this is expected on sparse/stale biometric data, not a failure.
* `GET /api/reports/mainline/history-cards?line={line}`
  * Fetches distinct `HistoryCard` dropdown values for the Main Line Cycle Time report.
* `GET /api/reports/mainline/stations?line={line}&historyCard={historyCard}`
  * Fetches distinct Stations for a specific line and history card.
* `GET /api/reports/mainline/data?line=...&historyCard=...&station=...&startDate=...&endDate=...`
  * Performs the 2-step dynamic query to return the massive Main Line cycle time payload.
* `GET /api/reports/poke-yoke/history-cards?line={line}`
  * Fetches distinct `HistoryCard` values for Poke Yoke (often shares the same logic as Mainline).
* `GET /api/reports/poke-yoke/stations?line={line}&historyCard={historyCard}`
  * Fetches distinct Stations for the Poke Yoke report.
* `GET /api/reports/poke-yoke/data?line=...&historyCard=...&station=...&startDate=...&endDate=...&engineNo=...`
  * Performs the dynamic query and returns bypassed Engine/Station data. 
  * If `engineNo` is provided, the API ignores date/station constraints and searches for the engine across all associated station tables.
  * If `station` is used, it supports multiple comma-separated stations (e.g., `ML-01,ML-02`).
* `GET /api/reports/poke-yoke/summary/data?line=...&historyCard=...&station=...&startDate=...&endDate=...`
  * Executes the heavy "Gaps and Islands" SQL query against the resolved station tables.
  * Automatically aggregates bypassed rows into consecutive sequences and calculates failure durations in seconds.

All settings for every module are in the single `appsettings.json` (`appsettings.Development.json` only overrides logging). Top-level sections:

| Section | Used by | Contents |
|---|---|---|
| `App` | Shared | `Version` - shown in the sidebar (`/api/configuration/version`) |
| `ConnectionStrings` | All | See below |
| `ShiftConfiguration` | Line reports, EB-RTM energy | Shift A/B/C (and pre-shift) start/end times |
| `DashboardDropdownValues` | Line reports | Values of the header's Line dropdown |
| `Mqtt` | All dashboards | Shared Kepware broker `Host` / `Port`; `StaleAfterSeconds` for the header MQTT pill (a feed is "receiving" if a message arrived within this window) |
| `FireHydrant` | Fire Hydrant | `Database` (alerts / pump count / pump duration tables), `Mqtt.Topic`, `Mqtt.OtherLocationsTopic` |
| `GasLeak` | LPG Gas Leak | `Database` (alerts table), `Mqtt.Topic`, `Mqtt.Lot1ValveCommandTopic`, `Mqtt.Lot2ValveCommandTopic` |
| `Ems` | EMS Renewable | `Database` (`SolarData`, `SolarLiveGraph`, `OtherPowerSource` tables), `Mqtt.SolarTopic` |
| `EbRtm` | EB-Real Time Monitoring | `Database` (readings / power-failure tables), `MaxDemandLimitKva`, `LogIntervalMinutes` (reading logging interval), `Mqtt.Topic` |

A dashboard can use a different broker by adding `Host` / `Port` to its own `Mqtt` section (e.g. `"EbRtm": { "Mqtt": { "Host": "...", "Topic": "..." } }`); otherwise it uses the shared `Mqtt` section.

**Connection strings**

| Name | Used by |
|---|---|
| `MainlineConnection`, `PokeYokeFilterConnection` | Line reports (Biometric, Main Line Cycle Time, Poke Yoke) |
| `SharedDataConnection` | Cross-database queries on 10.130.1.73 (`master`, 3-part names): the Poke Yoke data tables and the Fire Hydrant / Gas Leak / EMS / EB-RTM logging tables (each dashboard's database name comes from its `Database` setting) |
| `QHoldConnection`, `CylinderHeadLeakConnection` | Engine QHold, Cylinder Head Leak Rejection |

* **Filter Connections**: Used strictly to read mapping tables like `ehc.Vallam_StationMaster`.
* **Data Connections**: Because the Data Connections must query dynamically resolved databases (e.g., `[RE_Vallam_J1EA2_Mainline_DB].[dbo].[STN_data]`), the connection string's default `Database` is often set to `master` but requires cross-database query permissions.
* **Power BI report stored procedures** (`usp_GetQHoldReport`, `usp_GetCylinderHeadLeakRejectionReport`, `usp_GetCategorywiseReworkReport`, `usp_GetSummaryReport`) are created by hand in their databases - they are not part of this repository. The Summary Report returns HTTP 503 with a clear message if its procedure is missing.
* The broker currently accepts anonymous plain-TCP connections on this network, so no MQTT credentials are configured.

## ✅ Do's and ❌ Don'ts

### ✅ Do's
* **Do ensure `TrustServerCertificate=True`**: When testing locally or without SSL certificates on the SQL Server, ensure connection strings bypass certificate validation.
* **Do use parameterized queries**: Dapper parameterization (`@Param`) is strictly used in backend services to prevent SQL Injection.
* **Do bump the `?v=` number** on a `<script>`/`<link>` tag in `index.html` whenever you change that JS/CSS file. Static files are also served with `Cache-Control: no-cache`, so browsers revalidate on every load; if a user still reports "missing" UI features after a deployment, a Hard Refresh (`Ctrl + F5`) clears it.
* **Do verify SQL Permissions**: The SQL login (e.g., `factreread`) must have global/cross-database `SELECT` permissions, as the app dynamically routes to databases like `REJILINE` and `RE_Vallam_J1EA2_Mainline_DB` based on user selection.

### ❌ Don'ts
* **Don't hardcode table or database names in the `ReportsService.cs` queries**: The application is built to scale across multiple factory lines. Always resolve the `DatabaseName` and `DbName` from `ehc.Vallam_StationMaster`.
* **Don't modify DOM Elements from JavaScript without verifying IDs**: The frontend scripts (`wwwroot/js/`) rely on strict HTML IDs (`pokeYokeStart`, `mainDashboardDropdown`). Changing IDs in `index.html` will break javascript logic silently.
* **Don't use `SELECT *` in Dapper queries**: Always explicitly select columns (e.g., `SELECT [Date_Time], [Stn_Number]...`). If a dynamic table lacks a specific column mapped by `*`, Dapper will throw a runtime exception.
